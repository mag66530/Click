# Постановка: Telegram-бот отзывов (review_bot) — как устроен, что было, что изменено

> Это описание того, что реально лежит в коде на ветке `review-bot-import`
> (папки `bot/`, `core/`, `migrations/`) — не идея, а разбор существующего проекта
> + внесённых правок. Написано подробно специально, чтобы можно было свериться
> построчно с тем, кто писал исходный код.

---

## 0. Что это вообще такое и чем отличается от остального Click

В репозитории `Click` теперь живут **две независимые системы**, которые оба называются
«отзывы», но не связаны друг с другом:

| | Существующий Click (`reviews.py`, `ПОСТАНОВКА-Отзывы.md`) | **Этот бот (review_bot)** |
|---|---|---|
| Что делает | Актуализация карточек + поиск неотвеченных отзывов на Яндекс.Бизнесе, ответ через LLM, публикация после подтверждения в веб-интерфейсе Click | Отдельный **Telegram-бот**: следит за почтой и площадками, сам присылает уведомления о новых отзывах в чат |
| Где живут данные | Конфиги проектов Click (`data_root()/<project_id>/...`) | Своя SQLite-база `review_bot.db` (модели в `core/database.py`) |
| Как получает отзывы | Playwright заходит на карточку Яндекс.Бизнеса | Почта по IMAP (письма-уведомления от Яндекс.Бизнеса и 2ГИС) + опционально Google Business (Playwright) + опционально Яндекс Бизнес API |
| Кто инициирует проверку | Человек нажимает кнопку в Click | Бот сам, по расписанию (каждые 15 минут) |
| Куда приходит результат | В интерфейс Click (веб) | В Telegram-чат, отдельными сообщениями с кнопками |

**Это не заменяет друг друга.** Технически можно использовать оба параллельно на разных
брендах, если хочется — они не конфликтуют по данным. Что из них в итоге останется —
отдельное решение, здесь не решается.

Дальше — только про **review_bot** (Telegram-бот).

## 1. Из чего состоит бот (по факту кода)

```
bot/
├── main.py              ← точка входа: запускает Telegram-бота + планировщик
├── keyboards.py          ← инлайн-кнопки под сообщениями
├── states.py              ← состояния диалога (FSM) для редактирования ответа
└── handlers/
    ├── admin.py           ← команды администратора (/add_brand, /list_brands, /status...)
    └── reviews.py          ← обработка нажатий на кнопки под карточкой отзыва

core/
├── database.py           ← модели БД (SQLAlchemy): Brand, City, Subscriber, Review
├── imap_parser.py        ← читает почту, парсит письма Яндекс.Бизнеса и 2ГИС
├── review_validator.py    ← проверка «жив ли отзыв» / «отвечен ли уже»
├── google_scraper.py       ← Playwright: неотвеченные отзывы Google Business
├── yandex_api_client.py    ← клиент официального Яндекс Бизнес API (был не подключён)
├── gpt_client.py           ← генерация текста ответа через LLM
├── publisher.py            ← публикация ответа на Яндексе через Playwright
└── scheduler.py             ← главный pipeline: обходит бренды, вызывает всё выше по расписанию

migrations/
├── init_db.py              ← создать таблицы с нуля
├── add_cookie_path.py       ← миграция: путь к сессии браузера у бренда
├── save_cookies.py          ← сохранить сессию браузера для публикации на Яндексе
└── add_subscriber_roles.py   ← НОВОЕ: миграция ролей подписчиков (см. раздел 4)
```

## 2. Модель данных — что хранится и как связано

### 2.1. `Brand` (бренд/компания)
Одна запись — один клиент бота (например «Инметпром»). Добавляется командой
`/add_brand` в самом боте (диалог: имя → промт → IMAP-логин/пароль → сервер).

Поля:
- `prompt_template` — инструкция для LLM, своя у каждого бренда (поддерживает `{name}`, `{text}`, `{city}`)
- `imap_login` / `imap_password` / `imap_server` — доступ к почтовому ящику, куда падают
  письма-уведомления от площадок
- `yandex_oauth_token` / `yandex_company_id` — **опционально**, для официального Яндекс
  Бизнес API вместо скрейпинга (было написано, но не подключено — теперь частично подключено, см. раздел 5)
- `cookie_file_path` — путь к файлу сохранённой сессии браузера для автопубликации
  ответа на Яндексе через Playwright

### 2.2. `City` (город/филиал бренда)
Просто список городов бренда, добавляется командой `/add_city`. Сейчас используется
слабо — реально город определяется из текста письма, а не из этой таблицы.

### 2.3. `Review` (история всех обработанных отзывов)
Одна запись на каждый увиденный отзыв. Статусы (`ReviewStatus`):

| Статус | Когда ставится |
|---|---|
| `PENDING` | Новый позитивный отзыв (4–5★), ответ сгенерирован, ждёт решения модератора |
| `APPROVED` | Одобрен и опубликован (или отмечен вручную как отвеченный) |
| `EDITED` | Модератор отредактировал ответ перед публикацией |
| `NEGATIVE` | Негатив (1–3★) — ответ **не генерируется**, только алерт |
| `DELETED` | Отзыв успел исчезнуть с площадки до обработки |
| `FAILED` | Ошибка при попытке опубликовать (капча, таймаут и т.д.) |

Используется как история + защита от дублей — прежде чем что-то слать в Telegram,
бот проверяет, нет ли уже записи с таким `review_url` в базе.

### 2.4. `Subscriber` (кто получает уведомления в Telegram)
Появляется автоматически, когда человек пишет боту `/start`. **До моих правок** —
плоский список: всем подписчикам уходило абсолютно одно и то же сообщение на любой
отзыв. Что стало — раздел 4.

## 3. Как проходит один отзыв от появления до Telegram (`core/scheduler.py`)

Каждые 15 минут (`setup_scheduler`, интервал жёстко задан в коде) для каждого бренда:

1. **Сбор сырых данных.**
   - `fetch_new_reviews_from_imap(brand)` — читает непрочитанные письма в ящике бренда,
     по отправителю определяет площадку (Яндекс vs 2ГИС), парсит текст письма regex'ами
     под конкретный формат письма каждой площадки, достаёт: имя автора, оценку, текст
     отзыва, ссылку на отзыв, город (если удалось распознать)
   - если у бренда есть сохранённая Google-сессия (`google_sessions/<бренд>.json`) —
     дополнительно `fetch_unanswered_google_reviews` заходит на страницу отзывов Google
     Business через headless-браузер и вытаскивает карточки без кнопки «Ответить»
   - **НОВОЕ:** если у бренда заполнены `yandex_oauth_token`/`yandex_company_id` —
     дополнительно запрашивается список отзывов через официальный API (раздел 5)

2. **Проверка дубликата.** Если `review_url` уже есть в таблице `reviews` — пропускаем,
   отзыв уже обработан ранее.

3. **Проверка «жив ли отзыв»** (`check_review_alive`) — HTTP-запрос на ссылку из письма.
   Между приходом письма и обработкой могут пройти часы, отзыв мог уже быть удалён
   площадкой (спам, жалоба и т.д.). 404 / редирект на главную / текст «отзыв удалён»
   в теле → статус `DELETED`, в Telegram не идёт.

4. **Проверка «уже отвечен ли отзыв»** (`check_already_answered` либо, для Яндекса
   с подключённым API, сверка через API — раздел 5). Если да → статус `APPROVED`
   с пометкой «уже отвечен на площадке», в Telegram не идёт.

5. **Негатив (1–3★).** Ответ **не генерируется** — сразу алерт в Telegram (см. раздел 4,
   там же деление по ролям).

6. **Позитив (4–5★).** Текст отзыва + промт бренда уходят в `generate_reply` (LLM,
   модель `llama-3.3-70b-versatile` через Groq API, не OpenAI, несмотря на название
   файла `gpt_client.py` — это унаследованное от OpenAI-совместимого клиента название).
   Сгенерированный ответ сохраняется в `Review.generated_reply`.
   - Если генерация упала с ошибкой — уходит отдельное уведомление об ошибке.

7. **Отправка в Telegram** карточки отзыва с кнопками `✅ Одобрить и опубликовать`
   / `✏️ Редактировать` (`bot/keyboards.py`).

### 3.1. Что происходит по нажатию кнопок (`bot/handlers/reviews.py`)

- **✅ Одобрить и опубликовать:**
  - Яндекс → пробует опубликовать автоматически через Playwright
    (`core/publisher.py`, использует сохранённую сессию браузера бренда).
    Успех/неудача (капча, таймаут) обрабатывается, статус обновляется.
  - 2ГИС / Google → **автопубликации нет.** Кнопки меняются на «📋 Скопировать ответ» +
    «🌐 Открыть отзыв» + «✅ Отметить как отвеченный» — человек публикует руками
    на площадке и жмёт «отмечено».
- **✏️ Редактировать** — бот переводит диалог в режим ожидания текста (FSM), следующее
  сообщение модератора сохраняется как `final_reply`, статус меняется на `EDITED`,
  снова предлагаются кнопки публикации.

## 4. Роли подписчиков — что было и что стало (моя правка, коммит `e11ddd3`)

### Было
`Subscriber` — просто `chat_id`. Функция `notify_all_subscribers` слала абсолютно
всем подряд одно и то же сообщение при любом событии: и позитив, и негатив, и ошибку
GPT получал каждый подписчик, без разбора должности и без разбора бренда.

### Стало
Добавлены поля `Subscriber.role` (enum `SubscriberRole`) и `Subscriber.brand_id`:

| Роль | Что получает | Формат |
|---|---|---|
| `OWNER` (начальство) | Только негатив (1–3★) | Короткий алерт: бренд, город, оценка, автор, обрезанный текст, ссылка — без кнопок |
| `MANAGER` (ответственный за бренд) | Все отзывы **своего бренда** — и позитив, и негатив, и ошибки GPT | Полная карточка; для позитива — с кнопками модерации, для негатива — подробности без кнопок (ответ на негатив не генерируется, публикуется вручную при необходимости) |
| `VIEWER` (просто в курсе) | Любой отзыв своего бренда | Одна строка: «📩 Новый отзыв: Бренд, Город — ⭐⭐⭐⭐», без текста и кнопок |

`brand_id = NULL` у подписчика означает «видит все бренды» — так помечены все
существующие подписчики после миграции (обратная совместимость: никто не «ослеп»
после обновления, пока роли не настроены явно).

Логика адресности — три отдельные функции рассылки в `core/scheduler.py`:
`_recipients(db, brand_id, roles)` фильтрует подписчиков по роли и (если задан)
бренду, `_send_to(...)` рассылает конкретный текст конкретному списку.

### Управление ролями
Не через команды бота — через **веб-панель Click**, новый раздел «🔔 Отзывы»
в верхнем меню (`subscribers_admin.py`, подключено в `streamlit_app.py`).
Список подписчиков (появляются сами по `/start` в боте), для каждого — имя (для
удобства в панели, не влияет на бота), роль, бренд, кнопка сохранить.

### Миграция для существующей базы
`migrations/add_subscriber_roles.py` — добавляет три новых столбца в таблицу
`subscribers`, все существующие записи получают `role='manager', brand_id=NULL`
(поведение как раньше — видят всё). Прогнать один раз:
```
python migrations/add_subscriber_roles.py
```

## 5. Проблема «в бота приходили уже отвеченные отзывы» — диагноз и правка (коммит `e09b027`)

### Причина
`check_already_answered()` в `core/review_validator.py` делал обычный `httpx.get()` —
скачивал HTML страницы **без выполнения JavaScript** — и искал в тексте маркеры вроде
`"ownerreply"`, `"ответ компании"`.

Яндекс.Карты и 2ГИС — JS-приложения (SPA): реальный контент карточки, включая текст
ответа компании, подгружается через JavaScript/XHR **после** первой загрузки страницы.
Сырой HTTP-запрос получает практически пустой каркас — маркеров там физически нет,
даже если ответ на площадке давно стоит. Проверка систематически отвечала «не
отвечен», отсюда повторные уведомления в бота на отзывы, отвеченные вручную мимо бота.

Дополнительно: URL, который извлекается из письма (`core/imap_parser.py`) — это
страница **организации целиком** (`yandex.ru/maps/org/{бренд}/{id}/`), а не конкретного
отзыва. Даже если бы JS выполнялся, проверка искала бы «есть ли хоть один ответ на
странице», а не «отвечен ли именно этот отзыв».

### Правка — переиспользован уже проверенный приём из Click, не изобретался новый

Первая версия правки (см. историю коммитов) полагалась на официальный Яндекс
Бизнес API с OAuth-токеном — рабочий, но требующий отдельной настройки токена
и **непроверенный на реальном ответе сервера** (имена полей в JSON — догадка).

Вместо этого нашёлся кусок кода **в самом Click** (`yb_playwright.py`, раздел
«ОТЗЫВЫ», уже описан в `ПОСТАНОВКА-Отзывы.md`), который **проверен на живой
карточке** (13 отзывов, 12 с ответом, 1 без — см. комментарий в файле) и решает
ровно эту задачу без всякого API-токена:

> Яндекс кладёт весь список отзывов готовым JSON прямо в открытую в браузере
> страницу — `window.__PRELOAD_DATA.initialState.edit.reviews.list`. У каждого
> отзыва есть `owner_comment` — если там есть текст, компания уже ответила.
> Это факт из данных страницы, а не догадка по вёрстке или ключевым словам.

Этот приём и портирован в бота (`core/yandex_preload.py`), **дословно тот же
JS-скрипт**, что уже работает в `yb_playwright.py` — не переписан заново и не
придуман по-новому. Отличие только в обвязке: у Click синхронный Playwright
(общий поток на все города), у бота — асинхронный (что уже было в проекте
для Google, `google_scraper.py`), поэтому дословный импорт одного файла в
другой невозможен, но логика идентична.

Что нужно, чтобы это заработало:
1. **Сессия Playwright** — `Brand.cookie_file_path`, тот же файл, что уже
   обязателен для автопубликации ответа на Яндексе (`core/publisher.py`,
   `migrations/save_cookies.py`). Если она уже настроена для публикации —
   для этой проверки ничего дополнительно настраивать не нужно.
2. **Новое поле `Brand.yandex_permalink_id`** — числовой ID организации из
   ссылки раздела «Отзывы» в Яндекс.Бизнесе: `yandex.ru/sprav/<ID>/p/edit/reviews/`.
   Миграция: `migrations/add_yandex_permalink_id.py`, дальше заполнить вручную
   на каждый бренд (см. подсказку в самой миграции).

Как сопоставляется отзыв из письма (там нет ID) с отзывом из `__PRELOAD_DATA`:
по той же «сигнатуре» (оценка + автор + начало текста), что и в первой версии
правки — эта часть без изменений, `core/yandex_api_client.review_signature`.

### Порядок проверок в `core/scheduler.py` (кто кого подстраховывает)
Для каждого бренда за прогон, для отзывов с площадки «yandex»:
1. **`core/yandex_preload.py`** (основной способ) — если есть сессия и
   `yandex_permalink_id`
2. **`core/yandex_api_client.py`** (запасной способ) — если есть OAuth-токен,
   но способ 1 недоступен или упал с ошибкой. ⚠️ Этот способ по-прежнему не
   проверен на реальном API-ответе (имена полей в `_ANSWER_KEYS` — предположение)
3. Старая проверка по HTML (`check_already_answered`) — если недоступны оба
   способа выше. Именно она и вызывала исходный баг.

Для 2ГИС официального аналога `__PRELOAD_DATA`-приёма в этом коде нет —
там проблема (недостоверная проверка «отвечен ли уже») остаётся нерешённой.
Возможные пути позже: аналогичный разбор состояния страницы 2ГИС (если у неё
похожий механизм — не проверялось), Playwright с реальным рендером JS
(аналогично `google_scraper.py` для Google), либо смириться и полагаться
на дедуп по `review_url` (отзыв в базе уже есть → повторно не пришлют, но
именно первый раз ошибка выше всё ещё возможна).

### ⚠️ Что нужно сделать перед тем, как полагаться на это в проде
1. Убедиться, что у бренда есть рабочая Playwright-сессия (`cookie_file_path`)
2. Найти и заполнить `yandex_permalink_id` для каждого бренда
3. Прогнать вручную, посмотреть в лог строку
   `[Бренд] PRELOAD_DATA: N отзывов на странице, M отвечено`
   — если модуль пишет `Не нашли window.__PRELOAD_DATA` или `сессия истекла`,
   нужно обновить сессию (`migrations/save_cookies.py`) или проверить
   `yandex_permalink_id`

## 6. Что почищено при переносе кода (коммит `90ccf8c`)

При заливке исходников через веб-интерфейс GitHub вместе с кодом попали:
- `cookies/*.json`, `google_sessions/*.json` — **сессионные токены** входа в Яндекс/2ГИС/Google
- `review_bot.db` — бинарник базы (может содержать реальные отзывы/переписку)
- `logs/*.log` — 23000+ строк рабочих логов
- `__pycache__/*.pyc`, служебные `indexing_*` файлы

Все эти файлы удалены из последнего коммита ветки, добавлен `.gitignore`, чтобы
не попадали повторно. **Важно:** они остаются в истории git на этой ветке (в коммите
`dd1e7ad`) — раз репозиторий приватный, не критично, но раз куки «засветились» в гите,
по-хорошему стоит перелогинить эти сессии (Яндекс/2ГИС/Google) заново.

## 7.5. Новое: сверка с таблицей заказанных отзывов (Google Таблицы) — план, не реализовано

### Что выяснилось из присланного файла
Есть помесячная Google Таблица (лист на месяц: «Сентябрь 2026» и т.д.) со **заказанными**
отзывами — это не органические отзывы клиентов, а отзывы, которые компания сама заказывает
под конкретный город и ключевое слово (SEO: слово должно попасть в текст отзыва). Колонки:

| Бренд | Площадка | Город | Адрес | Ссылка | План | Цена | Сумма к оплате | Опубликовано | Статус | Имя | Текст отзыва | Ключевые слова | Кол-во | Балл |
|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|

Исполнители публикуют отзыв на площадке от своего имени: **Инна и Иван** — Яндекс.Бизнес,
**Алексей** — 2ГИС. Сейчас кто-то вручную идёт на площадку, ищет — появился ли заказанный
отзыв, и вписывает факт (`Кол-во`, `Балл`) в таблицу.

### Что должен делать бот (решение подтверждено пользователем)
Когда бот видит новый отзыв (из IMAP/Google/2ГИС-парсинга — тот же pipeline, что уже есть),
**сверяет его с открытыми строками заказа текущего месяца** по правилу:
`Площадка совпадает` + `Город совпадает` + `Ключевые слова` из строки заказа встречаются
в тексте отзыва. При совпадении — **бот сам** вписывает в найденную строку: `Кол-во=1`,
`Балл=<оценка отзыва>`, `Опубликовано=<дата>`, `Имя=<автор>`, `Текст отзыва=<текст>`,
`Статус=Готово`. Ручной работы с этой таблицей быть не должно.

### Технически — план (не реализовано, нужны вводные от вас)
- Таблица — Google Sheets → интеграция через **Google Sheets API** (сервисный аккаунт,
  JSON-ключ) и библиотеку `gspread` (или `google-api-python-client`)
- Новый модуль `core/orders_sheet.py`: подключение к таблице, поиск открытой строки заказа
  по (площадка, город, ключевые слова ⊂ текст), запись факта
- Вызывается из `core/scheduler.py` сразу после сохранения отзыва в БД (шаг 2 pipeline,
  раздел 3) — параллельно с отправкой в Telegram, не вместо неё
- **Что нужно от вас, чтобы начать делать код:**
  1. Доступ к таблице — либо ссылка + расшарить на почту сервисного аккаунта (создам
     и пришлю почту), либо экспорт структуры (какая именно колонка "Площадка" — там
     значения "Яндекс"/"2ГИС"/"Google"? нужно свериться дословно)
  2. Что делать, если совпадений **несколько** (два заказа на один город с похожими
     ключевыми словами) или **ни одного** (отзыв органический, не по заказу) — молча
     пропускать, или как-то сигналить?
  3. Нужно ли **дополнительно** отмечать это в Telegram (например, отдельная реплика
     «✅ Засчитано в заказ №… (Магнитогорск, титановые трубы)») — или таблицы достаточно?
